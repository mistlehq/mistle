# Designer blueprints are pushed into canvas tabs

Mistle Designer may author a **Designer blueprint** as sandbox-side JSON, using `.mistle/designer/blueprint.json` as a conventional working file, but the first-pass dashboard integration should receive the JSON contents through a dashboard control tool and persist the current blueprint in the existing **Designer canvas tab** entry. The dashboard should validate the pushed JSON before updating tab state, without adding a separate current-blueprint persistence column and without reading, watching, or polling arbitrary sandbox files. This keeps the agent's sandbox authoring workflow flexible, reuses the existing canvas-tab workspace model, and leaves separately persisted or multiple blueprints for a later design.

The dashboard control tool should expose the first-pass blueprint document shape in its dynamic tool input schema so the Designer agent can construct valid JSON without inferring hidden constraints from dashboard code. The tool spec should describe required document fields, allowed item/link/action kinds, routing policy rules, dashboard-internal action hrefs, and the rule that links/actions/routing targets reference item ids rather than the top-level outcome.

Designer should use this tool as the first alignment surface for open-ended build requests. For a request such as "Build a triaging agent", Designer should sketch the intended workflow as a blueprint and show it in the Designer canvas before asking the user to choose a concrete existing sandbox profile or before creating/updating triggers. Existing product-resource inspection is still useful, but it should serve the proposed blueprint rather than becoming the first interaction pattern. When profile choice is unresolved, Designer should discuss "use existing profile" versus "create new profile" in chat after the workflow is visible rather than representing that setup decision in the blueprint graph.

Blueprints should be process-first. The graph supports only trigger nodes, agent steps, routing policies, and workflow outputs to show what will happen, such as "GitHub trigger: PR opened" -> "Agent reviews PR" -> "Agent posts review summary". Integration/provider details should live on the trigger node when they describe the source of the trigger. Integration setup, sandbox profile selection, provider-resource selection, and confirmation belong in chat or ordinary route tabs after workflow alignment, not as blueprint item kinds. The first renderer should not display item-state badges or setup edge labels because the canvas is for workflow alignment, not implementation progress tracking.

The blueprint tab should render as a compact title header plus a boxed, read-only React Flow canvas. The graph is the review surface; there should be no separate item inspector or side panel. Item kind, label, short description, and compact routing-policy summary should appear directly inside custom React Flow nodes. The graph is purely visual: it may support pan and zoom, but it should not expose node dragging, edge editing, or visible action buttons.

The renderer should lay out blueprint nodes top-to-bottom using the process links declared by the blueprint document. Because the initial hand-authored column layout produced clipped and unreadable diagrams even for small blueprints, dashboard layout should use ELK through `elkjs` for the first serious renderer pass. The blueprint document remains semantic Mistle product structure; ELK and React Flow nodes/edges are derived renderer state and are not persisted as blueprint source data.
