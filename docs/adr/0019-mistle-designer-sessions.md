# Mistle Designer uses one-to-one sandbox-backed sessions

Mistle Designer uses durable **Mistle Designer sessions** backed one-to-one by a sandbox instance with the `designer` purpose and a **Mistle Designer base image**, while durable configuration is written into real product resources such as draft **Sandbox profile versions** instead of a separate design-plan resource. The first implemented pass persists the user's initial prompt, route-backed **Designer canvas tabs**, and the associated designer sandbox instance id; it does not yet wire a live Designer chat runtime. Future chat history can carry **Designer recommendations** rather than separate recommendation records. This keeps the guided setup workspace independent from the configured agent's eventual **Agent runtime**, avoids duplicating sandbox profile configuration in a separate design model, and still lets Designer orchestrate integrations, provider configuration resources, triggers, publish, and launch with explicit user approval for side effects.

Designer session API access is first-pass user-only access: Designer permissions are organization-user permissions and are not supported as API-key scopes. Designer sessions may read and refresh scoped **Provider configuration resources**, and may perform approved itemized **Provider configuration changes**, but the first pass does not require detailed durable activity history for those provider-side changes. Integration authorization and trigger review continue to use existing route-backed product flows in **Designer canvas tabs**, with completion detected from control-plane resource state rather than page-to-agent callbacks.

Designer runtime startup uses the existing sandbox instance start workflow and sandboxd activation path, but its runtime inputs are Mistle-operated rather than target-profile configured. A **Mistle Designer session** uses deployment-configured Designer sandbox runtime settings and a deployment-configured **Mistle Designer base image**; ordinary sandbox sessions continue to use **Sandbox profile version configuration** and snapshots. The Designer base image is a distinct image contract that includes the built-in Designer runtime tooling, initially Codex and broadly useful tools such as `gh`; installing a provider CLI in the image does not grant provider access.

The initial Designer **Runtime plan** activates the Codex app-server from the Designer base image, configures Mistle-owned model access through managed egress, and wires **Mistle Designer resource access** through a Designer-scoped Mistle MCP route. Designer should use a Designer-specific Mistle MCP credential resolver scoped to the organization and **Mistle Designer session**, not an organization API key selected through **Mistle resource access** and not the setup-assistant profile/version token shape. The target **Sandbox profile version**'s **Agent runtime** and model choice remain user-authored product configuration and are independent from the runtime used by Designer itself.

Provider access for Designer is dynamic session access, not a runtime-plan mutation. A selected or newly connected provider such as GitHub may become available to the running Designer session through managed access checks and credential resolution without changing the accepted sandboxd activation payload. Session-time tool installation remains chat-visible sandbox workspace state produced by the Designer agent; tools that become broadly required should be promoted into the **Mistle Designer base image** later. Designer runtime plans may keep the sentinel `sandboxProfileId = "designer"` and `sandboxProfileVersion = 1` as a compatibility placeholder until non-profile-backed runtime plans justify a broader data-plane/runtime contract change.
