# Designer runtime connection refresh updates MCP and egress

Mistle Designer may refresh provider access inside an active **Mistle Designer session** after it finds or helps set up relevant **Integration connections**. A **Designer runtime connection refresh** installs the workflow-relevant provider MCP servers into the Designer Codex runtime in bulk, refreshes sandboxd's non-secret **Sandbox-local egress route matchers** so remote MCP traffic reaches managed gateway egress, asks the dashboard/runtime client to reload Codex MCP configuration for later turns, and authorizes provider MCP/API egress through a Designer-only gateway-to-control-plane route resolution path rather than mutating the active sandbox runtime plan. This supersedes the earlier assumption in ADR 0020 that Designer provider access could be dynamic through ambient managed access checks: Codex can reload MCP servers mid-thread, and gateway can enforce Designer-specific provider access by recognizing Designer-session egress and asking control plane to validate the selected integration connection against current organization state.

Provider integrations declare whether they support Designer runtime access and which provider tool ids, setup state, and gateway egress strategy apply. Designer should use this metadata to request one workflow-scoped refresh after setup or connection discovery rather than escalating capabilities one tool at a time. Inspection access can proceed after the refresh succeeds; provider-side mutations remain governed by Designer approval policy.

The first implementation should not add a separate persisted Designer runtime access set. For a Designer session, refresh derives the requested provider access from current organization **Integration connections**, validates the connection is usable and supported for Designer runtime access, and materializes the result into Codex MCP config plus sandboxd-local egress route matchers for the active sandbox instance. Designer provider refresh should not create new `sandbox_instance_runtime_plans` revisions; ordinary sandbox sessions continue to use compiled runtime-plan egress routes from profile integration bindings.

The refresh request should be made through Designer-scoped Mistle MCP tools and must identify the intended connection and provider tool ids explicitly. Designer dynamic egress must not infer connection intent from provider hostnames alone, but it also should not introduce a separate persisted access object or signed access reference. The provider MCP configuration should carry the selected integration connection id and installed provider tool ids as request metadata; gateway should recognize the request as coming from a Designer sandbox, call control plane to validate that the connection still exists and is usable for that Designer session, compile the provider routes for an in-memory binding with the same tool ids, match the current target request, and then proxy through the managed egress route returned by control plane.

The Codex MCP reload and sandboxd route refresh should be triggered by the dashboard/runtime client as part of completing the Designer runtime connection refresh, using the active Designer sandbox's Codex app-server JSON-RPC connection. Control plane owns validation and returns the provider MCP config plus non-secret route matchers to install; the client-side/runtime control path asks sandboxd to refresh its local egress routes, applies the Codex MCP config, and sends `config/mcpServer/reload`.

Gateway should determine Designer eligibility from data-plane sandbox instance purpose loaded with the active runtime plan. It should only call the Designer dynamic egress resolver when sandboxd has routed the request to managed gateway egress, normal runtime-plan matching is unmatched, the sandbox instance purpose is `designer`, and the request includes the selected integration connection id plus installed provider tool id metadata.
