# Designer integration catalog is generated

Mistle Designer may use a **Designer integration catalog** as a searchable runtime reference for static provider metadata such as aliases, integration target identities, setup methods, resource kinds, and provider caveats. The catalog is generated from typed integration/provider registry metadata into a committed Markdown artifact at `apps/control-plane-api/src/designer/runtime-references/integration-catalog.md` rather than rendered dynamically during Designer session creation or edited directly as Markdown, so the registry remains the source of truth while Designer agents get cheap local lookup without broad MCP discovery calls. Designer session creation copies the generated catalog to `.mistle/designer/references/integration-catalog.md` inside the Designer sandbox, keeping Mistle-owned runtime references separate from user project docs and Designer blueprint source files.

Designer should search the catalog before broad integration MCP discovery when it only has a user-facing provider name, but can use scoped MCP tools directly when it already has a target key or connection id. Live organization state, connection status, selected resources, and secret-adjacent setup data remain behind scoped MCP tools instead of being written into the catalog. The first catalog should be generated from existing registry fields rather than new Designer-specific alias or caveat metadata; add typed provider metadata later only when real Designer behavior shows a concrete gap. Workflow policy stays in **Designer managed instructions** so the catalog does not become a hidden instruction surface. The catalog does not replace MCP for live state: after resolving static target identity locally, Designer should use scoped connection and setup-status MCP queries instead of unfiltered connection lists.

The generated catalog should be covered by a deterministic drift check in the fast validation path when generation is cheap enough: regenerate the committed Markdown, compare it with the checked-in file, enforce a size budget, and verify required structure for representative providers. If generation proves too slow for fast validation, keep the full drift check in pre-push or CI and retain a narrower fast test for the rendered structure.
