# Codex Skill Mentions Resolve At Turn Start

Codex skill mentions remain editable composer text, and Mistle resolves conservative `$skill-name` tokens only when starting a Codex turn. At `turn/start`, Mistle uses the current runtime-discovered skill metadata to emit one structured skill input for each distinct enabled skill path that is identified by exactly one submitted token match; unresolved or ambiguous manually typed tokens remain text-only. Codex `skills/list` skill metadata requires a concrete path, and Mistle treats that path as required for mentionable composer skills.

We originally chose submit-time text resolution because the composer was a plain textarea and should not pretend to preserve rich token identity through edits, copy/paste, undo, or mobile input behavior. Duplicate skill names now require explicit user selection to preserve the selected skill path, so the shared session composer should move to a CodeMirror-backed plaintext document model with selected skill mention ranges instead of adding a second editor framework such as Lexical or maintaining a fragile sidecar range ledger on a textarea. CodeMirror becomes the common composer editing surface across runtimes, while Codex remains the runtime that consumes selected skill mention metadata as structured skill inputs.

Structured skill inputs are protocol metadata for Codex turn startup, not user-visible transcript content. The implementation should ship as one coherent composer migration rather than as separate user-visible releases, but should still keep the internal change sequence reviewable: introduce the composer draft contract, migrate the shared composer editing surface to CodeMirror, then wire selected skill metadata into Codex turn startup. The first pass still does not apply structured skill inputs to Codex steer or queued message submission because Codex currently injects skill instructions from the initial turn input path.

The single PR must prove the behavior at the request builder, shared composer, Codex controller, queued-submission boundary, and UI-state levels. In particular, tests should cover duplicate visible skill names with distinct selected paths, selected metadata invalidation when token text changes, stale selected paths blocking submit, typed ambiguous names staying text-only, and selected skill mentions being visually distinguishable from ordinary typed skill mentions.
